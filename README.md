# Драфт-помощник Dota 2 (патч 7.41)

Локальный инструмент для мидового игрока: показывает, **что делать в этом матче** — как играть лейн против их мида,
какие угрозы несёт их драфт и чем на них отвечать, что покупать (с ценами 7.41) и когда.

Работает офлайн, без сторонних API, винрейтов и телеметрии: только игровые данные вашего патча + правила, выведенные из механик.

## Онлайн

**<https://xsitraxs.github.io/dota-2/>** — открывается прямо в браузере, ничего ставить не нужно.

Сайт обновляется при каждом пуше в `main`, а workflow
[`.github/workflows/pages.yml`](.github/workflows/pages.yml) подстраивается под настройку
**Settings → Pages → Source**:

| Source | Что происходит |
| --- | --- |
| **Deploy from a branch** | GitHub сам собирает сайт из корня `main`; workflow в этом режиме только прогоняет проверки (линтер, движок и данные, распознавание, интерфейс) и в деплой не вмешивается |
| **GitHub Actions** | после тех же проверок workflow собирает чистый артефакт — только `index.html` + `assets/` + `data/`, без `tools/` и README — и публикует его через `actions/deploy-pages` |

В обоих режимах перед публикацией проверяются движок, данные, распознавание и интерфейс (jsdom), так что сломанные данные
или регрессия вёрстки в прод не уедут. Публикация идёт только с `main` и никогда из pull request (на PR — одни проверки).
Права токена разделены: у сборки и тестов только чтение (`contents: read`, `pages: read` — узнать режим Pages), запись
(`pages: write`, `id-token: write`) есть лишь у job публикации, который не выполняет код репозитория. Сторонние
действия закреплены полными SHA; эту политику проверяет `tools/test_ci.mjs`. Если API Pages недоступно на push в `main`,
прогон падает с понятной ошибкой, а не пропускает публикацию молча.
Кнопка **Re-run jobs** на странице Actions или ручной запуск workflow (`workflow_dispatch`) в `main`
перепубликуют сайт без нового коммита.

## Запуск локально

```bash
# из корня репозитория
python3 -m http.server 8000
# открыть http://localhost:8000
```

Или любой статический сервер: `npx serve .`, `php -S localhost:8000` и т.п. Приложение чисто статическое —
`index.html` + `assets/` + `data/`, все ссылки относительные, поэтому одинаково работает и в корне домена,
и по адресу вида `xsitraxs.github.io/dota-2/`.

## Что внутри

| Раздел | Что делает |
| --- | --- |

| **Герои** | Все 127 героев 7.41: цифры клиента, способности с маной/КД/описанием, врождённые способности, изменения в 7.41, мидовые планы (36 героев) или закуп по роли героя, сильные и слабые матчапы, теги механик |

| **Патч 7.41** | Патчноуты (7.41f → 7.40): общие изменения, предметы, герои — с переходами в карточки |
| **Тайминги** | Живой таймер матча: руны, святилище мудрости, Рошан, Торментор, день/ночь — с обратным отсчётом |

## Откуда данные

- **Игровые константы** — [odota/dotaconstants](https://github.com/odota/dotaconstants) (MIT): герои, способности с цифрами,
  предметы, патчноуты. Обновляются из клиента игры.
- **Иконки героев** — [M-Hasan-Ibrahim/Dota2HeroInfoAndIcons](https://github.com/M-Hasan-Ibrahim/Dota2HeroInfoAndIcons).
- Собранный снимок лежит в `data/` и закоммичен, чтобы приложение работало без сети.

## Обновление данных при выходе нового патча

```bash
node tools/build_data.mjs          # скачает свежие константы и иконки, пересоберёт data/, проверит файлы знаний
node tools/build_data.mjs --cached # пересоберёт из уже скачанного в tools/.cache (без сети)
node tools/build_data.mjs --offline /path/to/dotaconstants   # константы из локальной копии
node tools/build_templates.mjs     # если поменялись иконки: подписи для распознавания (нужен ImageMagick)
npm test                           # движок, данные, база знаний, документация и политика CI
```

Без `--cached` архивы источников скачиваются заново при каждом запуске (раньше однажды скачанный кэш использовался
бессрочно). Серия патча (`7.41`, дата выхода серии) и последняя буквенная версия из патчноутов (`7.41f`) хранятся
в `data/meta.json` раздельно: `patchSeries`/`latestPatchDate` и `latestVersion`.

Сборщик не просто копирует JSON: он **валидирует файлы знаний** (`data/kb/*.json`) — каждая ссылка на героя,
способность, предмет и тег механики должна существовать в текущих данных, а в текстах планов не должно быть
устаревших названий способностей (например, «Force of Nature» вместо «Nature's Call») и опечаток в них.
Та же проверка (`tools/datalib.mjs`) работает в `npm test` на закоммиченных данных. Сборщик также сообщает о героях,
для которых в источнике нет иконки, и удаляет из `data/icons/` файлы героев, которых больше нет в данных.

## Разметка героев и закуп по ролям

Теги механик (`data/kb/tags.json`) — это то, из чего собираются «Угрозы их драфта» и ответы на них предметами.
Разметка курируемая, но проверяемая: у каждого тега в `tools/taglib.mjs` есть правило с доказательством —
фразой из описания способности («Riki fades into the shadows, becoming invisible») или числом из клиента
(«магический урон одной способностью до 500»). Фраза обязана быть в предложении описания, а не в заголовке
характеристики: заголовки без контекста («DAMAGE REDUCTION:») раньше давали ложные теги. Что заведомо не годится,
описано в таблице `DENY` вместе с причиной (`Ringmaster: Spotlight` — «раскрывает невидимых», а не невидимость)
и проверяется тестом: опечатка в ключе способности или выдуманный тег — ошибка. Способности за шард/агханим и,
для тяжёлых механик, фасеты в доказательства не берутся: без покупки предмета их в игре нет, а тег читается как
постоянная механика героя.

```bash
node tools/suggest_tags.mjs                # чего не хватает в разметке и что не подтверждено
node tools/suggest_tags.mjs --tag=invis    # все герои с невидимостью и цитата-доказательство
node tools/suggest_tags.mjs --hero=axe     # что подтверждено у одного героя, вплоть до текстов способностей
node tools/test_tags.mjs                   # инвариант: каждая однозначная подсказка применена или отклонена
```

Закуп для героя собирается в три слоя. Курируемый мидовый план (36 героев) — точный, с порядком прокачки,
кривой игры и матчапами. Для остальных 91 героя (почти все не мидовые) работает закуп по роли из
`data/kb/archetypes.json`: керри, мид, оффлейн, поддержка, роумер. Роль определяется по ролям героя из клиента
(первый слот ролей — основная роль), а спорные случаи переназначены в поле `overrides` с объяснением: без них
Pudge получал бы мидовый закуп, а Mirana — керрийный. Стартовый стат-предмет и «свой» большой слот зависят от
атрибута героя (силовик-керри получает Armlet, ловкач — Manta, универсал — Diffusal). Интерфейс честно пишет,
что это сборка по роли, а не план под патч, и показывает советы роли. Третий слой — ситуативные ответы на теги
драфта противника, они добавляются к любому из двух первых.

## Проверки

Нужен Node.js `^22.22.2 || ^24.15.0 || >=26` (как требует jsdom 30; поле `engines` в `package.json`).

```bash
npm ci                 # один раз: dev-зависимости строго по package-lock.json (eslint, jsdom, yaml)
npm run lint           # eslint: recommended + no-unused-vars, eqeqeq, no-var, prefer-const
npm test               # движок, данные и база знаний, README, политика CI (без браузера, быстро)
npm run test:recognize # распознавание на синтетических скриншотах (нужен ImageMagick: convert или magick)
python3 -m http.server 8000 &   # для следующей проверки нужен запущенный сайт
npm run test:ui        # прогон интерфейса в jsdom: драфт, все вкладки, таймер, скриншот, ошибки загрузки
```

`npm test` — это четыре файла. `tools/test_engine.mjs` проверяет логику: формулы статов (с константами из патчноутов),
матчапы (QoP против Huskar — тяжёлый лейн), угрозы и контрмеры, комбо-правила, рекомендации по пикам (в том числе
что занятых героев не предлагают — на сотнях случайных драфтов), закуп и чеклист. `tools/test_data.mjs` — распаковщик
tar (обход путей, ссылки), сопоставление иконок, версии патча, все ссылки и названия в базе знаний, согласованность
`meta.json`, иконок и шаблонов распознавания и чисел в этом README. `tools/test_tags.mjs` сверяет разметку героев
с правилами подсказчика: каждая однозначная подсказка тега (невидимость, бурст, руты…) обязана стоять в
`data/kb/tags.json`, иначе её отклоняют строкой в таблице `DENY` с объяснением причины, а тег без правила движка
или с несуществующим героем — ошибка. `tools/test_ci.mjs` разбирает
`.github/workflows/pages.yml` и вычисляет условия запуска для push, pull request и ручного запуска, проверяет права
токена и SHA-закрепление и прогоняет скрипт определения режима Pages с поддельным `gh`.
`npm run test:ui` открывает страницу в jsdom с полифиллом `fetch`, кликами собирает драфт и проверяет вердикт, угрозы,
закуп и `localStorage`; отдельно — испорченное хранилище (`constructor`, `__proto__`, повторы), скриншот с пустыми
и неузнаваемыми ячейками и заполнение драфта только известными героями без повторов, ошибки загрузки шаблонов
и изображения, сброс во время распознавания, героев без иконок. Любая ошибка скрипта страницы — провал теста.
`npm run test:recognize` склеивает из настоящих иконок синтетические «скриншоты» (ImageMagick) и проверяет поиск сетки
и героев на испорченных кадрах (яркость, контраст, размытие, JPEG, масштаб, шум, две строки, полоса в большом кадре,
ручная нарезка), а также пустые слоты, частичные сетки, обрезанные карточки, сдвинутую рамку, разные размеры кадра,
кадры без карточек и границы ручной области. Сквозной инвариант: ячейка, выданная за распознанную, всегда верна.
Все проверки прогоняются в CI (на push в `main` и на pull request) перед публикацией сайта.

## Важно про патч 7.41

В 7.41 **фацеты удалены из игры**, а врождённые способности больше не зависят от уровней других способностей
(скейлятся от уровня героя). Поэтому в интерфейсе нет выбора фацетов: планы и советы построены на актуальных
наборах способностей 7.41.

## Распознавание скриншота

Вкладка «Скриншот» работает целиком в браузере и офлайн: кадр уменьшается, каждая ячейка превращается
в компактную «подпись» (разностный хеш 17×16 + средние цвета 4×4) и сравнивается с подписями локальных
иконок из `data/templates.json`. Никаких внешних сервисов, картинка не покидает браузер.

```bash
node tools/build_templates.mjs   # пересобрать подписи (после обновления иконок; нужен ImageMagick)
```

Порядок работы: автопоиск сетки по профилям яркости и градиента (границы области содержимого, шаг решётки,
полосы рядов, подгонка фазы сетки по узнаваемости карточек) → сравнение ячеек с иконками → до 5 кандидатов
на ячейку → решение по ячейке:

| Статус | Когда | Что видно в интерфейсе |
| --- | --- | --- |
| уверенно (`ok`) | близость лучшего героя ≤ 0.25, отрыв от второго ≥ 0.05 и отношение близостей ≤ 0.75 | герой выбран в списке |
| не определён (`weak`) | совпадение слабое или неоднозначное (в том числе герой без шаблона, надпись, посторонняя картинка) | «— не определён —» и кнопки-подсказки |
| пусто (`empty`) | ячейка однородная (пустой слот, фон, середина без деталей) | «пустая ячейка», без кандидатов |

Если автопоиск ошибся, колонки, строки и область задаются вручную (область за краем кадра обрезается, колонок
и строк — не больше 24), а любую ячейку можно поправить списком или кнопкой-подсказкой. Кнопки «В противники» /
«В союзники» заполняют свободные слоты драфта по порядку ячеек — только уверенно распознанными или выбранными
вручную героями, без повторов и без героев, которые уже стоят в драфте. Кадры больше 2560 px по длинной стороне
перед распознаванием уменьшаются.

Что проверено (только синтетика: настоящие иконки, склеенные в карточки; реальных скриншотов в репозитории нет):
подписи шаблонов считаются тем же путём, что и распознавание (`sampleRect` с автоуровнями), поэтому у собственной
иконки героя расстояние до своего шаблона нулевое, а пороги уверенного совпадения подобраны заново на 241 верной
карточке с искажениями (размытие, яркость, контраст, JPEG, шум, уменьшение до 55 %) и на посторонних картинках
(встроенные картинки ImageMagick, узоры, шум, надписи «BAN»/«Radiant», градиент) — у верных карточек отрыв от
второго кандидата не меньше 0.064, у посторонних не больше 0.061, поэтому пороги 0.065 и 0.73 разводят их с запасом.
Ложных уверенных ответов ни в одной проверке (ни на «чужих» карточках, ни на посторонних картинках) нет.
Главное ограничение — кадрирование: если портрет обрезан иначе, чем любой из 5 кадров шаблона (сдвиг кадра на ~11 %
его ширины), верхняя догадка верна лишь для части карточек, и распознавание честно оставляет их «не определён».
На **реальных** скриншотах экрана пика карточки обрезаны иначе, чем иконки в `data/icons/`, баны обесцвечены,
а ряды разделены подписями, — для таких кадров надёжнее задать область и сетку вручную (удобно нарезать по одному
ряду команды и заполнять драфт по частям). Чтобы авто-режим заработал и на настоящих кадрах, нужны образцы
карточек из игры — из них соберём дополнительные кадры шаблонов.

## Ограничения

- Это не статистика винрейтов: цифры берутся из клиента, а суждения о матчапах — из базы знаний репозитория,
  их стоит проверять на практике.
- Герой, добавленный после сборки данных, отобразится только тем, что есть в датасете.
- Винрейты и данные матчей намеренно не используются: инструмент должен работать офлайн и не зависеть от сторонних сервисов.
- Автопоиск сетки рассчитан на карточки героев на однородном фоне (экран пика, полоса пиков). На необычной
  вёрстке сетку стоит задать вручную: колонки/строки в панели «Сетка карточек». Герои без иконок в `data/`
  (сейчас `ringmaster`, `kez`, `largo`) распознаванию недоступны — их подставляет пользователь.
- Иконок этих трёх героев нет в источнике: репозиторий иконок последний раз обновлялся 18.03.2023, раньше их выхода.
  Картинки других героев вместо них не подставляются — в интерфейсе буквенный аватар. У репозитория-источника
  нет файла лицензии (сами портреты — арт Valve), поэтому право распространять иконки не подтверждено, см. `NOTICE`.
- Актуальность данных ограничена датасетом odota/dotaconstants (сейчас 10.8.0, патчноуты до 7.41f). Тайминги,
  планы и советы в `data/kb/` — ручная база знаний: ссылки в ней проверяются автоматически, а сами игровые суждения —
  нет; при расхождении источников (например, время первого Торментора) сверяйтесь с клиентом игры.
